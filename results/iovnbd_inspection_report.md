## 4. Timestamps and sampling rate

- **S-file**: `TIME SINCE START (ms)` is NOT reliable on its own — in
  `S-S3b.csv` it resets mid-file (row 2042: `2707520 ms -> 8 ms`, an
  apparent device/app restart), producing one large negative delta if
  used naively. The `DATE (YYYY-MO-DD HH-MI-SS_SSS)` column IS
  monotonic across the same reset point and is the reliable clock: median
  step 100 ms (10 Hz), with one real gap of 4,428 ms at the same reset
  point (a genuine data gap, not an artifact of the parsing — the vehicle
  did not stop recording, the phone app did). This matches the README's
  stated 10 Hz smartphone sampling rate.
- **V-file**: `Time Since Start of Day (seconds)` is clean and fully
  monotonic in the file checked, exactly 0.100000 s steps throughout (10
  Hz), matching the `Sample period (seconds)` column, which is a constant
  `0.1` in every row.
- **S and V row counts** are equal for 63 of the 72 Categorised pairs
  checked; 9 pairs differ by a small number of rows (mostly 1-2, up to a
  few hundred in two cases: `Vfa01` differs by 49 rows, `Vfa02` by 232
  rows). This means "Synchronised" does not guarantee exact 1:1 row
  alignment for every run — it must be verified per-sequence, not
  assumed, before any code treats S and V rows as index-aligned.

## 5. GNSS, IMU, and reference/ground-truth fields

- **GNSS (smartphone)**: `GPS LATITUDE/LONGITUDE/ALTITUDE/SPEED/ACCURACY/
  ORIENTATION`, satellite count as `"visible / total"` text.
- **GNSS (vehicle)**: `Latitude/Longitude/Velocity/Heading/Height/
  Vertical velocity`, satellite count as a plain number. The vehicle GPS
  is the higher-quality reference (professional-grade INS, per the
  README), so **the V-file's GPS/position stream is the natural
  ground-truth trajectory**, not the phone's.
- **IMU (smartphone only)**: accelerometer, gravity, gyroscope,
  magnetometer, device orientation (Euler angles) — all in the S-file.
  The V-file has NO raw accelerometer/gyroscope; instead it has
  `Indicated Longitudinal/Lateral Acceleration (g)` and `Yaw Rate
  (deg/sec)`, which are vehicle-CAN-derived, not raw inertial-sensor
  channels.
- **Wheel/odometry (vehicle only)**: four wheel-speed channels (rad/sec,
  one per wheel) plus `Steering Angle (degrees)` — this is the real
  odometry source, richer than the single `speed + steer_angle` pair
  `data/loader.py` currently expects.
- **No explicit "GPS outage" flag or column exists in either file.** GNSS
  outage windows are not natively marked in IO-VNBD; any outage window
  used for benchmarking must be a synthetic mask applied on top of real
  continuous GPS, exactly as `data/loader.py`'s existing
  `simulate_gnss_outages()` already does. This is a masking of real
  IMU/GPS data, not a claim that IO-VNBD contains real captured GNSS
  outages.

## 6. Field mapping: IO-VNBD -> NAVDRIFT

| IO-VNBD field (S-file unless noted) | NAVDRIFT field | Units | Conversion |
|---|---|---|---|
| `ACCELEROMETER X/Y/Z (m/s^2)` | `IMUSample.accel_x/y/z` | m/s^2 | direct, no conversion |
| `GYROSCOPE Yaw/Pitch/Roll (rad/s)` | `IMUSample.gyro_x/y/z` | rad/s | direct, but axis order/mapping (yaw/pitch/roll vs x/y/z) is NOT confirmed to be a 1:1 axis match — needs an explicit, documented axis convention, not a blind rename |
| `DATE (YYYY-MO-DD HH-MI-SS_SSS)` | `IMUSample.timestamp` | s (parsed to float seconds since sequence start) | parse string, use in place of the unreliable `TIME SINCE START (ms)` column |
| V-file `Wheel Speed FL/FR/RL/RR (rad/sec)` + wheel radius (NOT given in either CSV) | `OdometrySample.speed` | m/s | **cannot be converted without a wheel radius, which IO-VNBD does not publish in these files** — requires either an assumed radius (must be disclosed as an assumption, not silently baked in) or using `Indicated Vehicle Speed (km/hr)` / `Velocity (km/hr)` directly converted km/hr -> m/s (divide by 3.6) as a substitute, bypassing wheel radius entirely |
| V-file `Steering Angle (degrees)` | `OdometrySample.steer_angle` | rad | `radians(degrees)` |
| V-file `Latitude/Longitude (degrees)` | `GPSSample.latitude/longitude` | degrees | direct |
| V-file `Height (km)` | `GPSSample.altitude` | m | `* 1000` |
| V-file `Heading (degrees)` | `GPSSample.heading` | degrees | direct (already matches `loader.py`'s expected convention, 0=North) |
| V-file `Velocity (km/hr)` | `GPSSample.speed` | m/s | `/ 3.6` |

No conversion in this table was invented beyond straightforward unit
algebra (km/hr -> m/s, degrees -> radians, km -> m) that is directly
justified by the units printed in each column header. The gyroscope
axis-labeling question and the wheel-speed-to-linear-speed question are
flagged as open, not silently resolved.

## 7. Existing `data/loader.py` compatibility — NOT directly compatible

`data/loader.py`'s `IOVNBDParser` currently assumes a layout that does
not match the real dataset in three material ways:

1. **Directory/file layout**: it expects `<root>/run_NNN/{imu.csv,
   odom.csv, gps.csv}` — three separate per-signal files per run. The
   real dataset instead ships **one `S-<run>.csv` file** (all phone
   signals combined: GPS + IMU + magnetometer + orientation) and **one
   `V-<run>.csv` file** (all vehicle signals combined: GPS + wheel speed
   + steering + CAN-derived accel/yaw-rate). There is no `imu.csv`,
   `odom.csv`, or `gps.csv` anywhere in either archive.
2. **Column names**: none of `DEFAULT_IMU_COLS`, `DEFAULT_ODOM_COLS`, or
   `DEFAULT_GPS_COLS` (`timestamp`, `accel_x`, `gyro_x`, `speed`,
   `steer_angle`, `latitude`, etc.) match any real IO-VNBD column header
   verbatim. A real `col_map` override is required for every one of the
   three parsers before `parse_run()` can read a single real row.
3. **Sampling rate default**: `simulate_gnss_outages()` and `DRDataset`
   default to `imu_hz=100.0`. The real IO-VNBD smartphone stream is
   **10 Hz**, confirmed by direct timestamp inspection above, not 100 Hz.
   Every outage-length and window-length default computed from
   `imu_hz` would be silently wrong (10x too short in real seconds) if
   the real data were fed through unmodified.

None of this makes the existing pipeline unusable — `synchronize_sequence()`,
`simulate_gnss_outages()`, `compute_se2_poses()`, `compute_pose_deltas()`,
`NormStats`, `DRDataset`, and `build_dataloaders()` are all
signal-agnostic once fed a `Sequence` of `IMUSample`/`OdometrySample`/
`GPSSample` objects — but `IOVNBDParser.parse_run()` and its column maps
cannot be reused as-is. A **new parser function** (or a real `col_map`
plus a rewritten `parse_run()` that reads one combined S-file and one
combined V-file instead of three separate files) is required. This
report does not implement that change — per instruction, Phase 1 is
inspection only.

## 8. Train/test sequence suitability

Based on row counts observed in the Categorised Synchronised set (72
run pairs, ~29.7 hours of 10 Hz smartphone data by direct row count):

- Sequence lengths vary enormously: from under 200 rows (~20 s, e.g.
  `Vtb10` at 196 rows) to over 126,000 rows (~3.5 hours, e.g. `Vw04`).
  Very short sequences (well under a minute) are not usable for a
  200-sample sliding-window `DRDataset` with `window=200` at 10 Hz (would
  need `window` reduced to suit 10 Hz, since `window=200` at 10 Hz is 20
  seconds, not the 2 seconds it represents at the code's assumed 100 Hz).
- The 9 pairs with S/V row-count mismatches should either be trimmed to
  the shorter of the two lengths or excluded from the first pass, rather
  than assumed aligned.
- A reasonable first held-out test set, sequence-level (never row-level,
  to avoid leakage): pick 8-10 of the 72 run pairs, spanning different
  driver codes (`S`, `M`, `Vf`, `Vta`, `Vtb`, `Vw`, `Y`) and a range of
  durations, held out entirely from training. This has not been
  finalized or executed — it is a proposal for the next phase, not a
  split that has been created on disk.
